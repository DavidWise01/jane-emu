## AV-189 · Restore fallback ROM loading

### Observed source-level failure condition

The AV-173 instrumentation path attached an iframe load handler only after the optional NES source transformation succeeded. When any injected hook failed to match or the transformed NES script failed syntax validation, the fallback loaded the original NES cabinet but the parent never attached an equivalent ROM-ready handler. As a result, `ready` could remain false, and an early chosen cartridge could remain queued indefinitely.

### Fix

- Attach an original-cabinet iframe load listener in the fallback path.
- Set `ready` from the original cabinet's actual `romInput`, and replay the queued `.nes` file through the existing input event.
- Restore a fresh release fetch (`cache: 'no-store'`) to avoid reusing stale emulator HTML after GitHub Pages updates.
- Add `dashboard/av189_runtime.js`, an observation-only lifecycle log for booting, ready, fallback, ROM queue, ROM delivery, reported running frames and explicit errors. It records no ROM bytes and never presses controller buttons.
- Route the diagnostic module into existing **VERIFY** within the fixed **PLAY / LEARN / VERIFY** three-tool interface. Preserve the NES stage, input owner and learn tools.
- Add `tests/av189_runtime.test.cjs` to CI: checks fallback readiness wiring, queued-ROM replay, session isolation, fresh fetch, error states, and unchanged NES boot/handoff hooks.

### Browser acceptance remains outstanding

A passing CI regression proves that the programmatic fallback code is present and sound under the tested conditions. It does **not** prove that a real NES ROM has booted or that START reached the game. Phase 4 earns zero points until an actual browser session demonstrates those effects.
